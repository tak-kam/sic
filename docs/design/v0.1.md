# sic v0.1 design

Covers the design items listed in section 34 of the specification.
The first milestone is for this program to return `30`:

```text
fn main() {
    let x = 10;
    let y = x + 20;
    return y;
}
```

```text
Source -> Lexer -> Parser -> AST -> (Typed AST) -> IR -> Bytecode -> Verifier -> VM -> 30
```

The language is called `sic`. Source files use `.sic`, bytecode uses `.sicb`,
and `sic` is the prefix for OTel namespaces and internal identifiers.

---

## 1. Workspace and module layout

The implementation is a **workspace**, not a single crate. The reason is not
decoration; it is auditability.

- Whether the VM crate knows about the outside world becomes a property of the
  dependency graph, checkable by machine.
- A CI test can assert that `sic-vm` has no dependencies and never mentions
  `std::net`, `std::process` or `std::fs`, which is how "no implicit network
  access" from section 33 is enforced rather than merely intended.
- When the VM and the broker are split into separate processes later, the crate
  boundary is already there and does not have to be redesigned.

Crates are added in the phase that needs them, never up front.

```text
sic/
├── Cargo.toml                # [workspace] only; no dependencies at the root
├── docs/design/
├── crates/
│   ├── sic-core/             # phase 1: Span, SourceFile, Diagnostic, ID newtypes
│   ├── sic-syntax/           # phase 1: lexer, tokens, AST, parser
│   ├── sic-cli/              # phase 1: the `sic` binary
│   ├── sic-types/            # phase 2: Type, TypeTable, type checker
│   ├── sic-ir/               # phase 2: high-level IR and its builder
│   ├── sic-bytecode/         # phase 2: instructions, file format, encode/decode, disasm
│   ├── sic-compile/          # phase 2: IR -> bytecode
│   ├── sic-verify/           # phase 2: bytecode verifier
│   ├── sic-vm/               # phase 2: register VM (no external effects)
│   ├── sic-journal/          # phase 4: execution journal
│   ├── sic-broker/           # phase 3: capability broker
│   ├── sic-json/             # phase 7: a JSON parser
│   ├── sic-otel/             # phase 8: journal to OTLP
│   └── sic-plan/             # what a program may do, read from bytecode
└── tests/                    # end-to-end (source -> result)
```

Dependencies flow one way; cycles are not allowed.

```text
core <- syntax <- types <- ir <- compile <- bytecode
                                              ^
                                  verify -----|
                                      vm -----|
core <- journal <- vm
cli -> everything
broker -> core, journal        (never vm)
vm -> bytecode, core, journal  (never broker)
```

`sic-vm` and `sic-broker` do not depend on each other. They share only the
capability request and response value types, which live in `sic-core`. That
shared edge is the future IPC boundary.

### Phase 1 crates

Only `sic-core`, `sic-syntax` and `sic-cli`.

```text
crates/sic-core/src/
    lib.rs
    span.rs          Span, SourceFile, line index (byte offset -> line:col)
    diag.rs          Diagnostic, Severity, rendering
    id.rs            NodeId, FuncId, LocalId, ConstIdx, ... newtypes

crates/sic-syntax/src/

crates/sic-cli/src/
    main.rs          argument parsing by hand, no clap
    cmd/parse.rs     `sic parse FILE` -> AST dump
```

## 2. The v0.1 grammar

The grammar is constrained by the requirement that the parser stay simple
(section 4). So v0.1 leaves out assignment, loops, closures, generic
definitions, pattern matching, optional semicolons, and block expressions.

### EBNF

```ebnf
program     = { item } EOF ;

item        = fn_decl ;

fn_decl     = "fn" IDENT "(" [ params ] ")" [ "->" type ] block ;
params      = param { "," param } [ "," ] ;
param       = IDENT ":" type ;

type        = IDENT [ "<" type { "," type } ">" ] ;

block       = "{" { stmt } "}" ;

stmt        = let_stmt
            | return_stmt
            | if_stmt
            | expr_stmt ;

let_stmt    = "let" IDENT [ ":" type ] "=" expr ";" ;
return_stmt = "return" [ expr ] ";" ;
if_stmt     = "if" expr block [ "else" ( if_stmt | block ) ] ;
expr_stmt   = expr ";" ;
```

An `if` condition takes no parentheses; the mandatory block removes the
ambiguity instead, so there is no dangling else.

### Expressions (Pratt parser)

From loosest to tightest:

| Level | Operators | Associativity |
|------:|-----------|---------------|
| 1 | `\|\|` | left |
| 2 | `&&` | left |
| 3 | `==` `!=` | left |
| 4 | `<` `<=` `>` `>=` | left |
| 5 | `+` `-` | left |
| 6 | `*` `/` `%` | left |
| 7 | prefix `-` `!` | right |
| 8 | postfix `f(...)` `.field` | left |

A primary expression is an integer, float, string, `true`, `false`, `null`, an
identifier, or `(` expr `)`.

`&&` and `||` become short-circuiting in phase 2, where they lower to branches.
The v0.1 parser only accepts them.

### Lexical rules

- Identifiers: `[A-Za-z_][A-Za-z0-9_]*`
- Integers: decimal, `_` allowed as a separator (`1_000`), value is `i64`.
  Overflow is a lexer error.
- Floats: `1.5`, `1.5e-3`, value is `f64`.
- Strings: `"..."`. The escapes are `\" \\ \n \t \r \0 \u{XXXX}` and a
  backslash at the end of a line, which joins it to the next and eats the
  whitespace indenting it. Nothing else: no raw strings and no interpolation in
  v0.1. The continuation is there because two strings cannot be joined either,
  so without it a long literal is one physical line however long it is.
- Comments: `// to end of line` and `/* nestable */`.
- Whitespace: space, tab, CR, LF only. Other Unicode whitespace is rejected, so
  that characters which look alike but are not cannot slip in.
- Sources must be UTF-8. A BOM is rejected.

### Keywords

In use: `fn let return if else true false null allow type agent import requires
spawn await retry timeout`. Each of these was reserved before it was real, which
is what let it be added without breaking a program.

Still reserved, and an error to use ("reserved for future use"):

```text
approval as capability const enum for in loop match mut parallel secret
struct trust use while workflow yield
```

`process` and `budget` are deliberately not reserved: the first is the namespace
of the `process.exec` capability and the second is a setting inside an `agent`
body, so both have to lex as ordinary identifiers.

## 3. The AST

Analysis results live in side tables. The AST holds no types; the `TypeTable`
built in phase 2 maps `NodeId` to types, and "typed AST" means the AST plus that
table. The AST therefore never has to change shape to suit type checking.

```rust
// sic-core
pub struct Span { pub lo: u32, pub hi: u32 }          // byte offsets
pub struct NodeId(pub u32);                            // unique within a module

// sic-syntax::ast
pub struct Module { pub items: Vec<Item>, pub span: Span }

pub enum Item { Fn(FnDecl) }

pub struct FnDecl {
    pub id: NodeId,
    pub name: Ident,
    pub params: Vec<Param>,
    pub ret: Option<TypeExpr>,     // absent: derived from the body in phase 2
    pub body: Block,
    pub span: Span,
}

pub struct Param   { pub id: NodeId, pub name: Ident, pub ty: TypeExpr, pub span: Span }
pub struct TypeExpr{ pub id: NodeId, pub name: Ident, pub args: Vec<TypeExpr>, pub span: Span }
pub struct Ident   { pub name: String, pub span: Span }
pub struct Block   { pub id: NodeId, pub stmts: Vec<Stmt>, pub span: Span }

pub enum Stmt {
    Let    { id: NodeId, name: Ident, ty: Option<TypeExpr>, init: Expr, span: Span },
    Return { id: NodeId, value: Option<Expr>, span: Span },
    If(IfStmt),
    Expr   { id: NodeId, expr: Expr, span: Span },
}

pub struct IfStmt {
    pub id: NodeId,
    pub cond: Expr,
    pub then_block: Block,
    pub else_branch: Option<Box<ElseBranch>>,
    pub span: Span,
}
pub enum ElseBranch { Block(Block), If(IfStmt) }

pub struct Expr { pub id: NodeId, pub kind: ExprKind, pub span: Span }

pub enum ExprKind {
    Int(i64), Float(f64), Bool(bool), Str(String), Null,
    Path(Ident),
    Unary  { op: UnOp,  operand: Box<Expr> },
    Binary { op: BinOp, lhs: Box<Expr>, rhs: Box<Expr> },
    Call   { callee: Box<Expr>, args: Vec<Expr> },
    Field  { base: Box<Expr>, name: Ident },
}

pub enum UnOp  { Neg, Not }
pub enum BinOp { Add, Sub, Mul, Div, Rem, Eq, Ne, Lt, Le, Gt, Ge, And, Or }
```

Parenthesized expressions leave no node behind; the structure already records
what they meant. If formatting ever needs them back, they can be recovered from
the spans.

**Error recovery**: the v0.1 parser does not stop at the first error. It uses
`;` and `}` as synchronization points and collects several diagnostics, while
keeping recovery shallow.

**Tree depth**: recursive descent turns nesting in the source into depth on the
stack, and a `.sic` file is untrusted input, so the parser counts levels and
refuses more than `MAX_DEPTH` (256) with `E0214`. It is the same limit
`sic-json` puts on a document, for the same reason, and larger because a program
nests further than an answer does. Recovery cannot help here - there is no
diagnostic to write once the stack is gone - so the depth is checked before the
recursion rather than after. Hitting it ends the parse instead of recovering
from it: every level on the way out would report its own unclosed delimiter, and
one clear reason is worth more than a hundred.

What it counts is the **tree**, not the parser. A flat chain - `1 + 1 + 1 + ...`
or `a.f.f.f...` - is read by the Pratt parser's loops rather than by recursion,
so the parser stays shallow while each operator wraps what came before and the
tree gets one level longer. Every pass that walks the AST afterwards recurses on
that, and a seven-kilobyte file of three thousand terms took the process down in
`print::dump`, in name resolution and in type checking. So a chain spends the
same budget nesting does, and it is one budget rather than two because the two
are additive: a hundred nested parentheses each holding a hundred-term sum is
one path two hundred nodes long, and bounding them separately would bound their
product, which is not what a stack cares about.

This refuses programs that were legal, and that is a decision rather than a side
effect. The alternative was to make every walk iterative - an explicit work
stack in the printer, in name resolution, in type checking and in lowering -
which refuses nothing but has to be repeated for every pass added afterwards,
with nothing checking that it was. One check protects every consumer of the AST,
including the ones not written yet.

## 4. Type representation

Implemented in phase 2; only the representation is settled here.

```rust
// sic-types
pub enum Type {
    Unit,
    Bool,
    Int,        // i64
    Float,      // f64
    Str,
    List(TypeId),
    Fn(FnSigId),
    Trust(TrustKind, TypeId),   // section 19; never constructed in v0.1
    Error,                      // propagates errors and suppresses cascades
}

pub enum TrustKind { Llm, Verified, HumanApproved, Observed, UserProvided, Secret }
```

- Types are interned behind `TypeId`, so comparing them is comparing integers.
- v0.1 only ever produces `Unit`, `Bool`, `Int`, `Float`, `Str` and `Error`.
- `Trust` **reserves the slot and nothing more**. No construction path and no
  checking rules are written before phase 7. It is here early only because
  inserting a layer into `Type` later would mean rewriting every match.
- There are no implicit numeric conversions; `Int + Float` is an error, per the
  "explicit" priority in section 32.
- The type of `null` is `Error` in v0.1, which keeps it unusable until an
  option-like type arrives later in phase 2.

Type checking produces a side table keyed by `NodeId`, together with what each
name resolved to (a local slot or a function).

### What the operators accept in v0.1

The instruction set has integer arithmetic and nothing else, so the checker
allows exactly what the VM can execute:

| Operators | Operands | Result |
|-----------|----------|--------|
| `+ - * / %` | `Int` | `Int` |
| `< <= > >=` | `Int` | `Bool` |
| `== !=` | `Int` or `Bool`, both the same | `Bool` |
| `&& \|\|` | `Bool` | `Bool` |
| prefix `-` | `Int` | `Int` |
| prefix `!` | `Bool` | `Bool` |

`Float` and `String` are real types - they can be bound, passed and returned -
but no operator accepts them yet. Adding float arithmetic means adding opcodes,
verifier rules and VM cases together, which is a later phase rather than a
convenience.

### Inferring a return type

Functions are checked in declaration order. A function with no `-> Type`
annotation takes its return type from the first `return` in its body, and every
later `return` must agree. Calling a function whose type is not settled yet -
a forward reference, or recursion - requires the annotation (E0306).

That rule keeps inference to one forward pass with no constraint solving, and it
keeps the error message actionable: the fix is always to write the annotation.

## 5. High-level IR

**The HIR is the layer that preserves workflow semantics** (section 5). It is
the last place they exist before VM instructions.

- Control flow becomes basic blocks and terminators; structured syntax is gone.
- Retry, timeout, parallel, agent, approval and budget **stay as instructions**.
  Erasing them here would leave `sic plan` (section 30) with nothing to
  reconstruct a plan from.
- Locals are an unbounded set of virtual registers (`LocalId`). No SSA, which
  would be overkill for v0.1.

```rust
pub struct Hir { pub funcs: Vec<HirFunc>, pub consts: Vec<Const> }

pub struct HirFunc {
    pub name: String,
    pub params: Vec<LocalId>,
    pub ret: TypeId,
    pub locals: Vec<TypeId>,        // LocalId -> type
    pub blocks: Vec<HirBlock>,
    pub entry: BlockId,
}

pub struct HirBlock { pub id: BlockId, pub insts: Vec<Inst>, pub term: Terminator }

/// Instructions and terminators carry the span they came from. That is what
/// later fills the debug section, so a runtime failure can name a line.
pub struct Inst { pub kind: InstKind, pub span: Span }
pub struct Terminator { pub kind: Term, pub span: Span }

pub enum InstKind {
    Const { dst: LocalId, k: ConstIdx },
    Move  { dst: LocalId, src: LocalId },
    Un    { dst: LocalId, op: UnOp,  x: LocalId },
    Bin   { dst: LocalId, op: BinOp, l: LocalId, r: LocalId },
    Call  { dst: LocalId, func: FuncId, args: Vec<LocalId> },

    // ---- phase 3 and later: defined but never generated in v0.1 ----
    CallCap { dst: LocalId, cap: CapId, args: Vec<LocalId>, policy: CallPolicy },
    Spawn   { dst: LocalId, func: FuncId, args: Vec<LocalId> },
    Await   { dst: LocalId, task: LocalId },
    Log     { level: LogLevel, msg: LocalId, fields: Vec<(String, LocalId)> },
}

pub enum Term {
    Jump(BlockId),
    Branch { cond: LocalId, then_bb: BlockId, else_bb: BlockId },
    Return(Option<LocalId>),
    Fail(LocalId),
}

/// Workflow semantics. Never lowered into VM instructions; the runtime uses
/// this for scheduling.
pub struct CallPolicy {
    pub retry:   Option<RetrySpec>,    // attempts, backoff, which errors
    pub timeout: Option<Duration>,
    pub budget:  Option<BudgetSpec>,
    pub idempotency_key: Option<LocalId>,
}
```

v0.1 generates only `Const`, `Move`, `Un`, `Bin`, `Call` and every `Term`.

**What lowering to bytecode discards** is written into the `CAPABILITIES` and
`DEBUG` sections of the bytecode file, which is where `sic plan` reads it back.

## 6. The v0.1 bytecode instruction set

### Encoding

**Four bytes per instruction**, little-endian, in three forms.

```text
ABC : [ op:u8 ][ a:u8 ][ b:u8 ][ c:u8 ]
ABx : [ op:u8 ][ a:u8 ][     bx:u16   ]
AsBx: [ op:u8 ][ a:u8 ][    sbx:i16   ]
```

Fixed width makes instruction boundaries a matter of arithmetic (`len % 4 == 0`,
jump targets divisible by four), which keeps the verifier and the disassembler
simple. Saving a few bytes with a variable-length encoding is not worth it for
this language.

Register numbers are `u8`, so a frame holds at most 256 registers. Exceeding
that is a compile error.

### The instructions (30 in v0.1)

| Op | Form | Meaning |
|----|------|---------|
| `LOAD_CONST  a, bx` | ABx | `R[a] = K[bx]` |
| `MOVE        a, b`  | ABC | `R[a] = R[b]` |
| `ADD_I64     a,b,c` | ABC | `R[a] = R[b] + R[c]`, overflow fails |
| `SUB_I64     a,b,c` | ABC | |
| `MUL_I64     a,b,c` | ABC | |
| `DIV_I64     a,b,c` | ABC | division by zero fails |
| `REM_I64     a,b,c` | ABC | |
| `EQ          a,b,c` | ABC | `R[a] = R[b] == R[c]` (bool) |
| `NE          a,b,c` | ABC | |
| `LT          a,b,c` | ABC | |
| `LE          a,b,c` | ABC | |
| `GT          a,b,c` | ABC | |
| `GE          a,b,c` | ABC | |
| `NOT         a, b`  | ABC | `R[a] = !R[b]` |
| `JUMP        sbx`   | AsBx | `pc += sbx`, counted in instructions |
| `JUMP_IF     a,sbx` | AsBx | jump when `R[a]` is true |
| `JUMP_IF_NOT a,sbx` | AsBx | |
| `CALL      a,b,c`   | ABC | `R[a] = F[b](R[c..c+argc])`; argc comes from the callee |
| `CALL_CAP  a,b,c`   | ABC | `R[a] = cap[b](R[c..c+argc])`; the only way out of the VM |
| `SPAWN     a,b,c`   | ABC | `R[a] = task running F[b](R[c..c+argc])` |
| `AWAIT     a, b`    | ABC | `R[a] = the result of the task in R[b]` |
| `MAKE_OBJECT a,b,c` | ABC | `R[a] = a record of type T[b] from R[c..]` |
| `GET_FIELD a,b,c`   | ABC | `R[a] = R[b].field[c]` |
| `MAKE_LIST a,b,c`   | ABC | `R[a] = a list of R[b..b+c]` |
| `GET_INDEX a,b,c`   | ABC | `R[a] = R[b][R[c]]` |
| `LEN       a, b`    | ABC | `R[a] = the length of R[b]` |
| `FROM_JSON a,b,c`   | ABC | `R[a] = a value of type T[b] parsed from R[c]` |
| `RETURN      a`     | ABC | return `R[a]` |
| `FAIL        a`     | ABC | fail with `R[a]` as the error value |
| `HALT`              | ABC | stop; the sentinel of the entry frame |

**Instructions left out on purpose**, and why:

- `LOAD_NULL`, `LOAD_TRUE`, `LOAD_FALSE`: `LOAD_CONST` plus the constant pool
  already covers them. Section 7 says not to add opcodes beyond what is needed.
- `NEG_I64`: the compiler lowers it to `0 - x`, and folds it when the operand is
  constant.
- `RETURN_UNIT`: the compiler loads the unit constant and uses `RETURN`.
- Per-type comparisons such as `EQ_I64`: the verifier pins down the types, so a
  value at runtime always has the expected one and a single instruction can
  handle it without branching. Splitting them later is a decision for profiling
  data, not for now.

The calling convention places arguments in **consecutive registers**, as Lua
does. `CALL a, b, c` assumes the arguments sit in `R[c] .. R[c+argc-1]`, which
avoids variable-length operands and preserves the fixed four-byte encoding.

`CALL_CAP` arrived in phase 3; see
[capabilities.md](capabilities.md) for what it means and how the VM performs a
call it cannot perform. Its form is ABC rather than the ABx of the original
sketch, because an operand is needed for the argument base.

`SPAWN` and `AWAIT` arrived in phase 6; see
[concurrency.md](concurrency.md).

`MAKE_OBJECT`, `GET_FIELD`, `MAKE_LIST`, `GET_INDEX`, `LEN` and `FROM_JSON`
arrived in phase 7; see [agents.md](agents.md).

### Planned for later phases

```text
SET_FIELD   (nothing mutates a record in v0.1)
```

Every addition ships together with its verifier rule.

## 7. The bytecode file format

Extension `.sicb`. Little-endian throughout, lengths always precede data.

```text
+-------------------------------------------+
| MAGIC    "SICB"            4 bytes        |
| VERSION  major u16, minor u16             |
| FLAGS    u32                              |
| SECTION_COUNT u32                         |
| SECTION_TABLE [ kind u32, off u32, len u32 ] * n
+-------------------------------------------+
| section bodies, located by off/len        |
+-------------------------------------------+
```

Section kinds:

| kind | name | contents |
|-----:|------|----------|
| 1 | `CONSTANTS` | `tag u8` and payload: 0 unit, 1 bool, 2 i64, 3 f64, 4 string |
| 2 | `TYPES` | type descriptors, used by the verifier |
| 3 | `FUNCTIONS` | the function table |
| 4 | `CAPABILITIES` | the capability manifest (section 13) |
| 5 | `CODE` | every function's instructions, concatenated, 4-byte aligned |
| 6 | `DEBUG` | the source file names and a pc -> file:line:col table |
| 7 | `SIGNATURE` | signature; length 0 in v0.1 |

A function entry:

```text
name        : str (u32 length + UTF-8)
param_count : u8
param_types : u32 * param_count   ; indices into TYPES
reg_count   : u8       ; registers the frame needs; the verifier checks it
ret_type    : u32      ; index into TYPES
code_off    : u32      ; instruction index within CODE
code_len    : u32      ; number of instructions
```

The parameter types are in the file because the verifier needs them: they are
the initial state of the entry frame, and they are what a `CALL` site is checked
against. Leaving them out would mean either trusting the caller or not checking
calls at all.

A capability manifest entry:

```text
name        : str      ; e.g. "process.exec"
kind        : u8       ; read / write / exec / invoke
constraints : str      ; e.g. an absolute path, a sha256 pin
param_count : u8
param_types : u32 * param_count   ; indices into TYPES
ret_type    : u32
```

The signature is in the file for the same reason the function table carries
parameter types: the verifier checks a `CALL_CAP` without trusting whoever
produced the bytecode.

`sic plan` and `sic verify` can therefore report the permissions a bytecode file
requires **without executing any of it**, which is the foundation of section 30.

Sections may appear in any order and may be omitted. An unknown kind is **an
error**: silently ignoring one would create a channel for hidden data to ride
past signature verification.

## 8. Execution state of the register VM

```rust
pub struct Vm {
    program: Program,          // verified bytecode, read-only
    regs:    Vec<Value>,       // one register stack shared by all frames
    frames:  Vec<Frame>,
    heap:    Arena,            // section 14
    journal: Journal,          // section 21, phase 4
    fuel:    u64,              // instruction budget (a resource limit)
    status:  Status,
}

pub struct Frame {
    func:     FuncId,
    pc:       u32,             // absolute index into CODE
    reg_base: u32,             // where this frame starts inside regs
    ret_reg:  u32,             // absolute register in the caller to write into
}

pub enum Status {
    Running,
    Finished(Value),
    Failed(FailInfo),
    Suspended(SuspendReason),   // phase 5
}

pub enum Value {
    Unit, Bool(bool), I64(i64), F64(f64),
    Str(Handle), List(Handle), Object(Handle),
}
```

- Registers live in a single `Vec<Value>` sliced per frame by `reg_base`; no
  allocation per call.
- Everything suspend, save and resume need (section 15) is inside this struct.
  Serializing `regs`, `frames`, `heap` and `pc` is a checkpoint.
  As long as **no file handle or socket is ever part of VM state**,
  serializability holds structurally, which is a side benefit of capability
  separation.
- `fuel` decrements per instruction and fails at zero. It guards against endless
  loops and doubles as the metering unit for durable execution.

Limits, so that a runaway program stops on its own rather than exhausting the
host: at most 1024 frames, at most 65536 registers in total, and a default fuel
budget of 10 million instructions.

Through phases 1 and 2 the VM is fully deterministic and performs no external
effects. It does not even read `std::time`; anything that needs a clock becomes
a capability in phase 3. This is enforced rather than intended: a test in
`sic-vm` fails if the crate's sources mention `std::fs`, `std::net`,
`std::process`, `std::env`, `std::time` or `std::io`, or if it grows a
dependency outside the workspace.

The VM expects verified bytecode, and where the verifier has established a
property it does not check it again. Where an index could still be wrong because
a caller skipped verification, it fails the run with an internal error instead of
panicking: a hole in the verifier should end one run, not the process.

## 9. Responsibilities of the bytecode verifier

The rule is that **the VM may drop a runtime check only because the verifier
established the property**. The VM must never assume anything the verifier does
not guarantee.

The work is split in two. Decoding (`sic-bytecode`) turns bytes into a
`Program` and rejects anything that would stop one from existing: the magic, the
version, section ranges, unknown section kinds, a code section that is not a
whole number of instructions, element counts larger than the section holding
them. Verification (`sic-verify`) then works on a decoded program and checks what
it means: indices, jump targets, register initialization, types, and the limits
below.

### Structure (single pass)

1. `MAGIC`, `VERSION` and `FLAGS` are known
2. Section table entries stay inside the file, do not overlap, and no kind is unknown
3. `CODE` has a length divisible by four
4. Every opcode is known
5. Constant, type, function and capability indices are in range
6. `code_off + code_len` stays inside `CODE` for every function
7. `reg_count <= 256`, and every register operand is below `reg_count`

### Control flow

8. Jump targets are inside the function and on an instruction boundary
9. Each function's last instruction is `RETURN`, `FAIL` or `JUMP`, so control
   cannot fall out of the function
10. Unreachable code is a **warning**, not an error

### Data flow (forward abstract interpretation)

11. **Register initialization**: compute the set of defined registers at each
    instruction, **intersecting** at merge points. Reading an uninitialized
    register is an error.
12. **Type consistency**: the same pass tracks an abstract type per register
    (unit, bool, i64, f64, str, ...). A conflict at a merge point yields `Top`,
    and using a `Top` register is an error. This is what establishes that the
    operands of `ADD_I64` really are i64.
13. `CALL` arguments in `c..c+argc` are all initialized and correctly typed
14. `RETURN` returns a value matching the function's return type

The fixed point is computed with a worklist over blocks. Because merges
intersect and widen to `Top`, it converges monotonically.

### Resources

15. Limits on the number of functions, constants, instructions and registers
16. `CALL_CAP` never uses a capability index that the `CAPABILITIES` section does
    not declare (phase 3)

All errors are **collected**, not reported one at a time. The verifier takes a
`&[u8]` and contains no `unsafe`.

## 10. The execution journal event model

Per section 21, the journal is the **single source of truth** for durability,
tracing, metrics, logs, audit and replay. OpenTelemetry is derived from it
(section 22).

```rust
pub struct Event {
    pub seq:       u64,          // monotonic within a run; the authority on order
    pub run_id:    RunId,        // 128 bit
    pub task_id:   TaskId,
    pub span_id:   SpanId,       // 64 bit
    pub parent:    Option<SpanId>,
    pub kind:      EventKind,
}

pub enum EventKind {
    RunStarted   { workflow: String, args_digest: Digest },
    RunCompleted { result_digest: Digest },
    RunFailed    { error: ErrorInfo },

    FunctionEntered { func: String, src: SrcLoc },
    FunctionExited  { func: String },

    CapabilityRequested { cap: String, args_digest: Digest, attempt: u32 },
    CapabilityCompleted { cap: String, result_digest: Digest, duration_nanos: u64 },
    CapabilityFailed    { cap: String, error: ErrorInfo, attempt: u32 },

    // phase 5 and later
    TaskStarted { .. } TaskCompleted { .. } TaskFailed { .. }
    TaskSuspended { reason: SuspendReason } TaskResumed { .. }
    AgentStarted { .. } AgentCompleted { tokens_in, tokens_out, cost }
    ApprovalRequested { .. } ApprovalGranted { approver, .. }
    BudgetConsumed { kind, amount, remaining }
    CheckpointWritten { checkpoint_id, size }
    Log { level, message, fields }
}
```

Decisions worth stating:

- **Digests by default, not values** (section 27). Raw arguments and results are
  not written to the journal, so there is no default path by which a secret or
  personal data reaches telemetry. Replay that needs raw values happens only in
  an explicitly enabled recording mode.
- **`seq` is the authority on order**; the wall clock is an observation added
  afterwards. Replay determinism must not depend on time.
- **The event has no timestamp field at all.** A sink adds one as it writes, so
  `sic-journal` reads no clock and two runs of the same program produce the same
  stream. A test in the crate fails if it ever mentions `std::time`.
- Digests are SHA-256, implemented by hand in `sic-core` and checked against the
  FIPS 180-4 vectors. It is needed here and by the bytecode signature section
  later, which is what makes a real cryptographic hash worth writing rather than
  a fast non-cryptographic one.
- A digest over a sequence of values hashes each one with a tag and an explicit
  length, so that `["ab"]` and `["a", "b"]` cannot collide.
- The format is JSONL (phase 4), with a hand-written JSON writer and no serde.
  The journal is append-only, one event per line, so a truncated file still
  reads up to the truncation.
- `span_id` and `parent` exist from the start. The trace structure of section 23
  is fixed as events are produced rather than reconstructed later.
- The VM only **writes** to the journal. Where the events go (a file, stdout, an
  IPC channel) is up to the implementation of the `Journal` trait, so the VM
  crate never touches `std::fs`.

Deliberately left for later, with the reason:

- **No optimization passes.** Constant folding and dead block elimination are
  easy to add and easy to get wrong; nothing needs them yet.
- **Register allocation is `local n -> register n`.** Reusing one register for
  two locals whose lives do not overlap would need liveness analysis, and the
  only cost today is a larger frame.
- **`Float` and `String` have no operators.** Each one is an opcode plus a
  verifier rule plus a VM case, and they belong with the phase that needs them.
- **No garbage collector.** The arena is dropped when the run ends, per
  section 14.

A run looks like this:

```console
$ sic run examples/read-file.sic --journal run.jsonl

"hello from a file\n"

$ cat run.jsonl
{"ts":...,"seq":0,"run":"64dd...","task":0,"span":0,"parent":null,"event":"run_started","workflow":"main","args":"sha256:af5570f5..."}
{"ts":...,"seq":1,"run":"64dd...","task":0,"span":1,"parent":0,"event":"function_entered","func":"main"}
{"ts":...,"seq":2,"run":"64dd...","task":0,"span":2,"parent":1,"event":"capability_requested","cap":"fs.read","args":"sha256:88d243d0..."}
{"ts":...,"seq":3,"run":"64dd...","task":0,"span":2,"parent":1,"event":"capability_completed","cap":"fs.read","result":"sha256:31ddb35c..."}
{"ts":...,"seq":4,"run":"64dd...","task":0,"span":1,"parent":0,"event":"function_exited","func":"main"}
```

Neither the path that was read nor the contents that came back appear anywhere
in it.

Deliberately not in phase 4:

- **No `sic runs`, `sic explain` or `sic replay`.** They need runs to be stored
  somewhere and indexed, which is a decision about where state lives, not about
  the event model.
- **No recording mode that keeps values.** The mechanism for it is a flag on the
  journal, but it needs the trust and secret types of section 19 to decide what
  may be kept, or it becomes the leak it was meant to prevent.
- **No OpenTelemetry export.** That is phase 8, and it reads this stream.
- **Events are recorded, never read back.** A journal reader belongs with
  replay.
- **No task, agent, approval, budget or checkpoint events.** Each arrives with
  the phase that can produce it. Adding a variant later costs one match arm,
  unlike a layer inserted into a type, so there is nothing to gain by
  reserving them now.

## Phase 6 broken into units of work

The design is in [concurrency.md](concurrency.md). The units:

| # | Unit | Done when |
|---|------|-----------|
| 6-1 | `Task<T>`, `spawn` / `await`, policies in the grammar and the checker | a policy on a pure call is rejected, and `main` cannot return a task |
| 6-2 | Type descriptors, `SPAWN` / `AWAIT`, the policy section | the verifier knows `await` on a `Task<Int>` gives an `Int` |
| 6-3 | Tasks in the VM and the scheduler | two tasks are recorded as waiting at the same time |
| 6-4 | Retry in the VM, the timeout in the request | a retried call shows every attempt in the journal |
| 6-5 | Timeout in the broker | a slow child is killed, and a capability that cannot honour a deadline says so |
| 6-6 | Tasks in checkpoints, format 0.2 | a 0.1 checkpoint is refused rather than half-read |
| 6-7 | Task events, `attempt` on capability events | the task field stops being zero |

Two things changed shape in the process, both because the implementation showed
the design was short:

- **The type section holds descriptors, not tags.** A one-byte tag cannot say
  what `AWAIT` produces. This is what the section was for in the original
  design; phases 2 to 5 only ever needed the primitives.
- **A policy lives in its own section, keyed by pc.** A four-byte instruction
  has no room for retry and timeout, and a side table can be read without
  executing anything - which is what `sic plan` will need.

## Phase 7 broken into units of work

The design is in [agents.md](agents.md). It was built in two parts, because the
structured data half is worth having on its own: a capability that returns JSON
needs exactly the same machinery an agent does.

| # | Unit | Done when |
|---|------|-----------|
| 7a-1 | `type` declarations, records, struct literals, field access | a type containing itself is rejected |
| 7a-2 | Lists, indexing, `len` | an empty literal without an annotation is rejected |
| 7a-3 | Records and lists in the arena and in checkpoints | a nested value survives being written out |
| 7a-4 | The five data instructions and their verifier rules | the verifier knows what `GET_FIELD` produces |
| 7a-5 | `sic-json`: a parser with limits, and an isolation test | trailing commas and duplicate keys are refused |
| 7a-6 | `FROM_JSON` and schema validation | a mismatch names the path that failed |
| 7b-1 | `llm.invoke`, deferred by the broker | a model call suspends the run |
| 7b-2 | `agent` declarations, lowered to a call and a validation | nothing in the VM knows what an agent is |
| 7b-3 | Budgets per call site, surviving checkpoints | exceeding one fails the run |
| 7b-4 | The budget event | a budget is visible while it is spent |

Three things changed shape during the work:

- **The type section carries field names.** Instructions still address a field
  by position, but a JSON document addresses fields by name, so validation needs
  both.
- **An empty list is a constant.** `MAKE_LIST` takes its element type from its
  elements, which an empty list has none of, and a list cannot be modified, so
  one empty list can be shared.
- **Agent-specific journal events were dropped.** Emitting them would require
  something below the checker to know what an agent is, which is exactly what
  the lowering avoids. They become worth their cost when an agent is a loop
  rather than one call.
